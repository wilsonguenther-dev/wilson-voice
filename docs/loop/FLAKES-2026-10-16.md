# FLAKES-2026-10-16 — main goes green

Item `yap-flakes-2026-10-16`. Two integration tests went red on `main` while the
code under test was right: `per_chunk_deadline_not_per_take`
(`desktop/src-tauri/tests/dictation_chunked.rs`) and the elapsed-clock test in
`meeting_manual_start_stop` (`desktop/src-tauri/tests/meeting_manual_start_stop.rs`).
Prior evidence: recorded red on `main` at `90d7861` (Obsidian `Projects/Yap.md`,
2026-09-27), and three consecutive red main CI runs on step `cargo test`.

## How it was soaked

`scripts/flake-soak.sh <test-target> <filter> <runs>` — one `yes > /dev/null`
busy loop per CPU (`sysctl -n hw.ncpu` = 12 on the soak box, an Apple-silicon
Mac, aarch64-apple-darwin), their PIDs recorded and killed by an EXIT trap, the
test binary compiled once with `--no-run` BEFORE the load starts, then
`cargo test --features custom-protocol --test <target> [<filter>]` run `<runs>`
times from `desktop/src-tauri`. Every exit code is read bare. A run that exits 0
having run ZERO tests (a filter that matches nothing) is counted as a failure.
The other loop lane was building on the same box at the same time, which is
extra load, not less.

## 1. `per_chunk_deadline_not_per_take`

**Shape before.** 12 windows x a fake decode that sleeps 200 ms, against a
300 ms per-chunk budget. Each window had **100 ms** of headroom (0.5x the decode).
One late `thread::sleep` return or one late `recv_timeout` wake > 100 ms trips
that window's deadline, `chunks_failed` becomes 1, the test fails.

**Why not an injectable clock.** The per-window budget is
`rx.recv_timeout(transcribe_timeout)` in `TranscriptionManager::leased`
(`src/transcription.rs`): a REAL wait on a worker thread, because it is the hard
bound on a wedged native decode. Simulating its time means replacing the channel
wait with something a fake clock can drive, which changes the thing it guards.
The item allows that only as a no-behaviour-change seam; there is no such seam
here, so the fallback was taken.

**Shape after.** 24 windows (the same 5 s window geometry over 120 s of ramp
instead of 60 s) x 50 ms against a **1 s** budget. Total decode 1.2 s > 1 s
budget, so the take could never have fit a per-take wall; each window keeps
**950 ms** of headroom (19x the decode, up from 0.5x). Both facts are asserted
statically before anything runs (`delay * 24 > budget`, `delay * 10 < budget`),
and the runtime asserts are unchanged in kind: 24 windows, 0 failed, not
degraded, 24 decodes, elapsed > budget, elapsed >= 24 x delay.

## 2. `meeting_manual_start_stop` — the elapsed clock

The YV111 sleep-then-count window was already gone on main (the test waits with
`support::wait_until` on the payload, `Sink::payload_seconds`). What remained
load-sensitive was the lag bound: `observed - payload <= 2 s` with `observed`
measured from an `Instant` taken BEFORE `start()`. That folds `start()`'s own
cost (SQLite rows, the fake capture engine, the OS-12 preflight diagnostics)
into the measured lag — a slow `start()` on a loaded box eats the slack.

**After.** For every recording status the sink received:

* `elapsed_seconds` never decreases (unchanged);
* never FAST: `payload <= receipt - before_start` (unchanged; arithmetic, load
  cannot break it);
* never SLOW: `receipt - after_start <= elapsed_seconds + 1 s + one tick`, where
  `after_start` is taken once `start()` has RETURNED and so is never earlier than
  the controller's own start `Instant`. The ticker computes
  `floor(started.elapsed())` immediately before calling the sink, so a ticker
  that wakes late also computes a later elapsed: scheduler delay does not widen
  this lag; only the few lines between `started.elapsed()` and the sink push can,
  and one tick (60 ms) bounds that.

The bound went from `1 s + 1 s` to `1 s + 60 ms` — **tightened**, not widened —
because the load-sensitive term (`start()`'s cost) is no longer inside it. A
half-rate clock (lag ~1.5 s at the third second) and a stalled clock both still
fail. `support::wait_until` stays the only wait, `TICK_DEADLINE` (30 s) stays
the death detector, and the per-emit minimum gap (`>= TEST_TICK / 2`) stays: the
ticker parks on a condvar with a relative timeout per iteration
(`TickerStop::wait(tick)` in `src/meeting_control.rs`), so load can only
lengthen a gap, never shorten it.
