- YV39: Receipt-sequenced reliable paste — the fixed clipboard-restore sleep is gone. The old path was `write clipboard → ⌘V → sleep 400 ms → restore prior clipboard`, and the chord is only *enqueued* at that point: a busy or slow target reads the pasteboard whenever its event loop gets to it, so the fixed delay loses the race and the user gets their OLD clipboard pasted back (Handy's #502; Yap had the same bug shape). New `desktop/src-tauri/src/paste_tx.rs` ports Handy's `src-tauri/src/paste_tx/` handshake: the transcript is published with `declareTypes:owner:` as a lazy pasteboard PROMISE (no data on the board) alongside the three `org.nspasteboard` concealment markers so well-behaved clipboard managers skip it, and AppKit's `pasteboard:provideDataForType:` callback on our owner object IS the read receipt. Only receipts observed AFTER the ⌘V injection count (an earlier read is a clipboard manager reacting to the change itself, not the paste target), the restore waits a 200 ms quiet period past the LAST receipt (Chromium probes, then reads), and it only fires while we still own the board — `changeCount` unchanged and no `pasteboardChangedOwner:` — so a user copy in the meantime always wins. `RESTORE_TIMEOUT` (8 s) and `FAILED_INJECTION_TIMEOUT` (500 ms) bound the wait; the no-receipt outcome deliberately diverges from Handy and KEEPS the transcript on the clipboard as plain text (never lose text — a chord nobody read never landed), logged at WARN. Publishing and the chord run on the main thread (AppKit services promises on the main run loop, and Yap's CGEvent ⌘V is main-thread-only per the SIGTRAP note), while the 15 ms-poll waiter and the guarded restore run off it, so the receipt handshake adds nothing to release→paste latency. `paste.rs` loses `dispatch_paste_on_main` + `paste_cmd_v_main_thread` and with them BOTH fixed sleeps (the 400 ms restore and the 30 ms pre-chord settle); the clipboard snapshot moved inside the transaction, taken after any still-open transaction is settled, so it captures the user's clipboard instead of a previous transcript promise. Behaviour preserved: `auto_paste=false` still only copies, the YV21 wrong-target guard still short-circuits to clipboard-only, and a paste failure still records `pasted=false` with the transcript left on the clipboard — but the reason is now logged at ERROR with the frontmost app (`paste failed: … (frontmost=…)`), closing the audit's silent `pasted=false` (yap-logs finding 3, 1 of 181 transcripts with zero diagnostics). Cancellation-safety (handy-os finding 10): `AppState.paste_generation` is an `AtomicU64` bumped by every cancel/interrupt BEFORE the recording check — so a cancel arriving while a previous take is still transcribing still invalidates it — captured by `stop_and_transcribe` at key-release and re-checked immediately before the paste; a stale take is copied but NEVER pasted.
