The three new ones close the review's BLOCKING finding, and the bomb they
describe was built and measured against the SHIPPED function first:

  $ ls -l bomb.tar.bz2                     384 bytes
  $ tar -tvjf bomb.tar.bz2                 pkg/model.onnx   314,572,800 B
  # against feat/yv123 @ 314c576, before the fix:
  RESULT: Ok("/tmp/yv123-bomb-out/pkg/model.onnx")

  # after the fix, same archive:
  RESULT: Err("archive expands past the 268435456-byte extraction cap")

384 bytes in, 300 MB out, and the function returned Ok — the cap did not fire
late, it did not fire at all. The counter had reached 512, because the entry
states its size TWICE (a PAX `size=` record ahead of the ustar header) and the
cap was reading the field tar-rs ignores while tar-rs streamed the other one.

The fixtures are hand-written ustar streams piped through /usr/bin/bzip2 — no
binary blob is committed. `tar::Builder` refuses to emit a `../escape` entry, so
a guard tested only against archives a well-behaved writer produces would be a
guard tested against the wrong input. The writer is itself checked by
`the_fixture_writer_emits_an_archive_the_system_tar_agrees_with`, which lists
the same fixture with `/usr/bin/tar -tjf`.
