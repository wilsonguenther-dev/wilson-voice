Forward findings for YV123 (its acceptance criteria are affected TODAY)
════════════════════════════════════════════════════════════════════════════

1. `grep -rn "bzip2-sys\|libbz2" Cargo.lock returns no match` is ALREADY
   unsatisfiable, before YV123 starts. `sherpa-onnx-sys` declares
   `[build-dependencies] bzip2 = "0.4"`, which pulls `bzip2-sys`, and both are
   in `desktop/Cargo.lock` as of this commit:

     $ grep -n 'name = "bzip2' desktop/Cargo.lock
     539:name = "bzip2"
     549:name = "bzip2-sys"

   The intent behind the criterion survives — nothing links libbz2 into a
   shipped binary; it is a BUILD dependency of a build script, used to unpack
   the prebuilt native archive. YV123's test must assert "no bzip2-sys in the
   runtime graph of `wilson-voice`", e.g. `cargo tree -p wilson-voice -e normal`,
   not "not in Cargo.lock".

2. There is a cheaper vendoring hook than the one O6/finding #23 costed.
   `sherpa-onnx-sys`'s build.rs checks, in order:
     SHERPA_ONNX_LIB_DIR      — an already-EXTRACTED lib tree
     SHERPA_ONNX_ARCHIVE_DIR  — a directory containing the `.tar.bz2`, which
                                the build script then extracts itself
     (else) download from GitHub Releases
   Finding #23 only names the first, which is the expensive one: something has
   to produce and cache an extracted tree in CI and at release. The second
   means a checked-in (or LFS/artifact-fetched) 19.5 MB archive plus one env
   var in ci.yml and release.yml is enough, and the sha256 can be asserted on
   the archive exactly as the model catalog does.

3. Upstream asset hashes measured while wiring this item, for the mirror:
     sherpa-onnx-pyannote-segmentation-3-0.tar.bz2  (7.0 MB)
       sha256 24615ee884c897d9d2ba09bb4d30da6bb1b15e685065962db5b02e76e4996488
     wespeaker_en_voxceleb_CAM++.onnx  (29,292,684 B)
       sha256 c46fad10b5f81e1aa4a60c162714208577093655076c5450f8c469e522ec54ef
   The archive extracts to `sherpa-onnx-pyannote-segmentation-3-0/model.onnx`
   and `model.int8.onnx`; this item uses the fp32 one.

4. The load path REFUSES bad bytes before onnxruntime sees them, and that is
   load-bearing for YV123's archive work: handing `Ort` an unextracted
   `.tar.bz2` aborts the process (SIGABRT, uncatchable from Rust — see M3).
   `looks_like_onnx` turns that into `model_load_failed`. It cannot catch a
   truncated-but-valid-headed file; the sha256 YV123 verifies before the path
   is ever sent is the layer that does.
