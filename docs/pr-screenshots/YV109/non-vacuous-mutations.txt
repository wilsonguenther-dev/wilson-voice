YV109 — non-vacuous mutations. Each patch was APPLIED, the named tests RUN, and
the patch REVERTED (`git diff desktop/src-tauri/src/` is empty on the branch).
Six mutations, six reds. Run 2026-08-15.

Why these six: the item's whole claim is that a two-track transcript comes out in
the order it was spoken, and there are exactly four ways that claim can be true
by accident — the renderer never had to sort, the clock rate never had to be
measured, the origin never had to be rebased, or the fixture was too easy to tell
the difference. One mutation each, plus one for the labels and one for a stale
corpus.

M1 — the renderer stops sorting
    src/meetings.rs :: render_transcript — `lines.sort_by(...)` deleted

    cargo test --test two_track_phase_e2e
      a_two_source_clock_offset_meeting_renders_one_ordered_me_them_transcript FAILED
      without_the_rebase_four_pairs_render_in_the_wrong_order                  FAILED
      test result: FAILED. 2 passed; 2 failed
    cargo test --test meeting_eval meeting_eval_two_track_ordering
      meeting_eval_two_track_ordering_survives_the_clock_mismatch              FAILED
      test result: FAILED. 0 passed; 1 failed

    NOTE — this one found a real hole while it was being run. The first cut of
    the E2E rendered only `db.list_meeting_segments`'s output, which SQLite
    already returns `ORDER BY start_seconds, track, created_at` — so M1 left the
    main E2E green and only the control went red. The E2E now renders the SAME
    rows twice, once in insert order (one whole track after the other, which is
    the shape the renderer has to fix itself) and once from SQL, and asserts the
    two agree. That is what makes the line above read "2 failed".
