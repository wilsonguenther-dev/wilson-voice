BLOCKING 1 — CI red: meeting_diagnostics_row::a_completed_meeting_carries_its_
             thermal_and_battery_readings, `left: [Fair], right: [Fair,
             Serious, Fair]`.

Root cause, confirmed: a wall-clock race, not a logic error. RampProbe advances
one step per read on the CONTROLLER's ticker thread; the test slept a fixed
TEST_TICK * 8 (320 ms) and then asserted EXACT equality on a path that needs six
samples at a 40 ms tick. Eight sleeps of 40 ms plus per-iteration work already
exceeds the budget on an idle box, so the margin was 0-1 ticks; a loaded GitHub
macos-14 runner delivered two.

Fix: the test now waits for the ramp instead of for the clock.
`RampProbe::ramp_fully_observed()` is true once `steps_read() > ramp.len()`. The
ticker body is strictly sequential (read → observe → emit → sleep), so the
(n+1)-th read cannot start until the n-th sample was folded in under the
diagnostics lock — which makes that counter a happens-before proof, observable
from outside the controller. `wait_for` polls it against a 30 s deadline, so a
genuinely stuck ticker still fails the suite by name rather than hanging it.
Widening the sleep was rejected: it cannot make a starvable-thread assertion
reliable, only less often wrong.

FALSIFIED before shipping. The failure would not reproduce under load alone
(16 then 128 spinners + `nice -n 20`, 12 and 10 runs: 0 failures — a 12-core
M-series schedules sleeping threads too well), so the CI condition was injected
directly: a 35 ms delay inside `RampProbe::thermal()`, which runs ON the ticker
thread. Two temporary control binaries, identical but for the wait:

`stop()` set an AtomicBool and then `join()`ed a thread mid-`sleep(TICK_INTERVAL)`.
