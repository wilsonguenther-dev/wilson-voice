YV105 — are these tests evidence, or are they green because everything is green?

A matrix-wiring item is exactly the kind of change that can ship thirty-one passing
assertions that prove nothing: five of them are source scans by nature, and the rest
drive state machines that already had their own suites. So each new test was checked by
BREAKING the shipping code it claims to drive and confirming the right assertions go red
— and, for the five absence tripwires, by making the missing call site appear.

Every mutation below was applied to `main`'s code, run, and reverted. The working tree
at commit time is clean of all of them (`git status` in the PR body).

MUTATION 1 — the 14.4 gate leaks onto the mic-only door.
  src/meeting_asr.rs: `if capture == MeetingCapture::MicPlusSystemAudio {` → `if true {`
  This is the regression row 12 exists to prevent: "system audio needs a newer Mac"
  becomes "meetings do not work on your Mac" for every pre-14.4 user.

MUTATION 3 — the in-flight guard stops discarding our own notifications.
  src/input_format.rs, in `observe_output`: `if self.aggregate_work_in_flight {` → `if false {`
  This is Hyprnote's documented infinite loop (fastrepl/hyprnote #1654): the listener
  answers its own rebuild with another rebuild.

  FIRST ATTEMPT: the row-14 suite stayed GREEN, and that was a real defect in this
  branch's test, not in the code. The assertion read `matches!(action, Ignored(_))`, and
  with the guard removed the events are still `Ignored` — by the 500 ms debounce instead
  — so a genuinely broken guard produced an identical result. Fixed by asserting the
  exact reason (`Ignored(InputFormatWatch::GUARDED)`), that nothing is left QUEUED
  (`has_pending_rebuild()`), and that the watchdog's own settle tick is guarded too.

  cargo test --test matrix_row14_output_device_change   (after the fix)
    test the_rebuilds_own_notifications_cannot_start_another_rebuild ... FAILED
    (5 others ok)
  and clean, unmutated: 6 passed; 0 failed.
